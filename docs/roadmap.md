# Ticketsmith — Roadmap

| Phase | Deliverable | Value when done |
|---|---|---|
| **0. Foundations** ✅ | Repo, strict TS, Biome, dependency-cruiser, vitest, tsdown, CI, kernel (Result, errors, logger), base CLI | `ticketsmith --version` and `pnpm check` green |
| **1. JIRA** ✅ | Config + profiles + keychain, `init`, `doctor`, `JiraCloudTicketSource`, `adfToMarkdown`, `discover`, `list`, `show` | **Usable on day one:** `ticketsmith show PROJ-123 \| claude` |
| **2. MCP** ✅ | `ticketsmith mcp` with `jira_get_issue` and `jira_search`, masking, session vault, audit | Use your tickets from Claude Code |
| **3. Projects and onboarding** ✅ | Profile → project with **optional, independent integrations**; `project init` resumable wizard; storage (`project.yaml` + `knowledge/` shareable, `local/project.sqlite` via `node:sqlite`); ticket-source step with JIRA investigation (issue types, workflows, fields); `project status/refresh/add/remove/use/link/export/import`; automatic migration of existing profiles; commands and MCP tools enabled per configured integration | One command sets up a project; knowledge persists and can be shared through a separate repo |
| **4. DB reads** | Databases onboarding step (any number of named databases, optional groups sharing a schema; schema investigated into SQLite and knowledge), read guard (adversarial tests first), `MysqlDatabaseAdapter`, MCP `db_select`/`db_schema` and group lookups with masking and vault, `db ask`, DB `doctor` | Claude finds accounts and investigates data |
| **Distribution** ✅ | Public repo (MIT, fresh history, private-terms guard), npm package with update notice, Claude Code plugin + marketplace (`npx ticketsmith@latest mcp`, `investigate-ticket` skill), `pnpm release` + tag-triggered publish workflow | Anyone installs it with npm + two plugin commands and gets updates automatically |
| **5. Repos** (live check pending) | Repositories onboarding step (any number of repos on any host): dedicated clones, runtime per repo, deterministic project maps and cross-repo connections in knowledge, MCP `repo_list`/`repo_files`/`repo_search`/`repo_read`, repo `doctor` checks | Claude understands back and front before touching them |
| **6. Agent + bugs** (live check pending) | `ClaudeCodeCliRuntime` (MCP tools only, local HTTP tool server, revealed outputs), `process <KEY>`/`--next`, `bug` and `repo-analysis` playbooks, `knowledge_read`/`knowledge_search`, `project refresh repos --deep`, agent `doctor` check | First end-to-end analysis |
| **7. Approved DB writes** (live check pending) | Write guard, `db_propose_change`, `changes show/approve/reject`, preflight, rollback scripts | Service requests resolved with one approval |
| **8. Code changes (L3)** (live check pending) | `ticketsmith code <KEY>`: worktree and branch per ticket from the fix branch, file tools confined to it (no shell), `code_run_tests`/`code_diff`, tests re-run by Ticketsmith, ask-before-push, PRs through GitHub or Bitbucket Cloud APIs or a link for any other host | Bugs fixed with human review |
| **9. New functionality** (live check pending) | Feature playbook: spec + clarifying questions → design plan the human approves → coordinated back/front worktrees from the feature base branch → new tests → schema changes as migration files → ask before PRs (requirements §4.15) | New functionality tickets implemented end to end with two human checkpoints |
| **10. Classification + knowledge + evals** (live check pending) | Rules + LLM, `classify`, `knowledge add`, golden set, `eval` | Measure before raising autonomy |
| **11. Reports, service requests, L2 JIRA** (live check pending) | `ticketsmith comment`/`transition` posted by a person with `y/N` (no agent write tools), `allowWrites` per ticket source, `markdownToAdf`, suggested transitions | The agent's reply reaches the ticket after you read it |
| **12. Extension** (partly live-checked) | PostgreSQL with dialect-aware guards and one adapter contract suite for MySQL and PostgreSQL (verified on PostgreSQL 17); `AgentSdkRuntime` (`project agent`; live check pending with an API key); JIRA Data Center (`wikiToMarkdown`/`markdownToWiki`; live check pending on a real server); Metabase integration and `metabase publish` (verified against Metabase 0.56 in Docker) | More teams can use it: other engines, self-hosted JIRA, CI runs, Metabase questions |
| **14. Investigations without a ticket** (live check pending) | `investigate "<question>"`: the agent run of `process` with a question instead of a ticket, for projects with or without a ticket source; read-only tools (no `db_propose_change`, no code tools); the question masked with the run's vault; `investigate` playbook with findings by severity, confidence and evidence; `out/investigations/<date>-<slug>/` (ADR 0031) | Proactive reviews of a feature, flow or data, saved, budgeted and audited |

Each later phase also adds its own onboarding step (databases in 4, repositories in 5).

## Next

What we would build next, in this order. Each phase must keep the design goals of the requirements: secure by construction, useful the same day, a new provider is a folder, measurable, simple. Every integration is optional and read-only for the agent; anything that writes goes through a person, as in phases 7, 8 and 11.

| Phase | Deliverable | Why it matters |
|---|---|---|
| **13. Trust and contributors** | Close the live checks of phases 5–12. Write `SECURITY.md`: threat model (what the agent can and cannot reach, masking limits, prompt injection from ticket text) and how to report a vulnerability. Write `CONTRIBUTING.md`: setup in one command, how to add a provider, the definition of done. **Sandboxed test runs**: `code_run_tests` executes tests the agent can edit, so run it without network or access outside the worktree (e.g. `sandbox-exec` on macOS, a container on Linux). **Contract suites** for `TicketSource`, `TicketWriter` and `PullRequestHost`, like the database one: a provider is done when it passes them. Issue templates and labelled starter issues. Coverage in CI. | People trust and extend what they can verify. Contract suites turn "add a provider" into a clear, reviewable task for newcomers. |
| **15. Observability for bugs** | **Sentry** (issues, events and stack traces for the error a ticket mentions, mapped to `repo/file:line`). **Log search** through one port with **Grafana Loki** and **Datadog** providers: bounded time windows, row limits, masked output. MCP tools `errors_*` and `logs_search`, read-only. | The fastest path from "it fails" to the cause is usually the error tracker and the logs, not the code. This makes the bug playbook much stronger. |
| **16. More ticket sources** | **GitHub Issues**, **Linear** and **Zendesk**, each a `TicketSource` provider passing the contract suite, with optional writers for L2 comments. **JIRA OAuth 2.0 (3LO)** for companies that forbid API tokens. | Ticketsmith becomes useful to open-source maintainers, product teams and support desks, not only JIRA users. |
| **17. More code hosts and engines** | **GitLab** (cloud and self-managed) and **Azure DevOps** pull requests; **Bitbucket Data Center**. **SQL Server** and **MariaDB** as database dialects passing the adapter contract. Optional **read replica** per database for reads (requirements, open question 4). | These cover most company setups. Each one is a provider plus contract runs, with no changes to the core. |
| **18. Team knowledge** | **Confluence** and **Notion** as read-only knowledge sources (runbooks, specs), searchable through `knowledge_search` and masked like everything else. **Slack**: read the threads linked from a ticket, masked; optionally post a short "run finished" notice to a channel the project names. | The answer to a ticket often lives in a runbook or a thread. The agent should find it, not the person. |
| **19. Runs at scale** | `ticketsmith watch`: on a schedule or in CI with the Agent SDK runtime, process new tickets into drafts (`out/`, never posted). Autonomy levels enforced per ticket type from `ticket-types.md`. A local HTML report of runs and evals: cost, time, accuracy and regressions per playbook. | Teams can let it prepare work overnight and measure whether it is getting better, before granting more autonomy. |

**Not planned:** tools that let the agent write on its own (posting, merging, running SQL without approval), DELETE or DDL against databases, and integrations whose only purpose is to move data out of the company. These go against the security principles and will not be accepted as contributions.

One phase at a time, each planned and approved before coding (see `CLAUDE.md`). A phase is done when `pnpm check` is green and it was verified against the real systems.
